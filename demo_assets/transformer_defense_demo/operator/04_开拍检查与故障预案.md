# 开拍检查与故障预案

## 一、启动

在项目目录中打开终端：

```bash
source ~/.zshrc
conda activate audiorescue-real
test -n "$DASHSCOPE_API_KEY" && echo "API Key 已加载"
AUDIORESCUE_UI_FIXTURE=0 python app.py
```

如果页面已经在运行，不要重复启动第二个实例。

## 二、录制前 10 分钟检查

- [ ] 页面是真实模式，不是 fixture；
- [ ] 实际麦克风已被 AudioRescue 识别；
- [ ] 虚拟输出选择 `BlackHole 2ch`；
- [ ] 接收端或录音软件的输入选择 `BlackHole 2ch`；
- [ ] 会议软件自带自动增益、强降噪和美声已关闭或降到最低；
- [ ] 输出扬声器是耳机，避免回授和啸叫；
- [ ] `raw`、`enhanced`、`quiet` 三种模式都已预试；
- [ ] 模式切换后页面状态会更新；
- [ ] API Key 已加载，网络正常；
- [ ] 已提前生成一次测试建议完成预热；
- [ ] 三份 Markdown 资料可以正常选择和解析；
- [ ] 点击“开始新会议”后悬浮窗会自动打开；
- [ ] 浏览器退到后台后悬浮窗仍可操作；
- [ ] 位置编码问题可以得到不超过三句话的正确回答；
- [ ] 系统通知、微信、QQ、邮件和浏览器密码提示已关闭；
- [ ] 画面中没有 API Key、私人文件名和绝对路径；
- [ ] 手机和电脑电量充足，存储空间足够；
- [ ] 已完整彩排一次并计时。

## 三、固定测试语

降噪对比，两遍完全一致：

> 在嘈杂环境下，我们仍然希望会议中的每一句话都清楚可懂。

小声增强对比，两遍完全一致：

> 现在环境很安静，但我需要小声发言，请比较两次接收到的人声响度。

## 四、成功门槛

### 实时降噪

- 原声可以明显听到稳定背景噪声；
- 增强后背景噪声下降；
- 人声仍然连续、可懂，没有严重金属音或吞字；
- 接收端确实使用 BlackHole，而不是物理麦克风。

### 小声增强

- 环境保持安静；
- 轻声经过 `quiet` 后比 `raw` 更容易听清；
- 没有明显爆音、泵动或把轻声当噪声削掉。

### 会议助手

- 字幕能够跟随主要发言；
- Q/K/V 段结束后的建议指向位置编码或多头注意力；
- 优势段结束后的建议提醒局限，而不是直接致谢；
- 位置编码问题回答准确且简短；
- 虚构数字压力问题不会被系统顺势承认。

## 五、故障预案

| 风险 | 先做什么 | 正式录制的稳妥备选 |
|---|---|---|
| 会议软件找不到 BlackHole | 完全退出会议软件，确认 AudioRescue 已启动，再重开会议软件 | 使用已验证能识别 BlackHole 的软件，不临时换 QQ 或微信 |
| 降噪差异不明显 | 换成持续风扇声，固定麦克风和噪声位置 | 重新录制这一小段，不改变后期音量 |
| 小声增强反而变小 | 确认背景安静、正对麦克风，模式稳定后再说 | 正片只保留通过预演的一组对比 |
| 字幕延迟 | 句子缩短，句间停顿 0.5–1 秒 | 后期压缩等待时间，但不伪造字幕内容 |
| API 建议超时 | 先预热一次，确认网络，上传小型 Markdown | 重新录制会议助手段，不必重拍音频段 |
| 建议提前收尾 | 核对预设与议程文件，换回两个指定触发点 | 只保留通过预演的真实请求镜头 |
| 问题回答跑偏 | 使用固定的位置编码问题，确认三份资料均加载 | 结束旧会议，重新开始一个干净上下文 |
| 悬浮窗被浏览器拦截 | 允许本地页面弹窗并重新开始会议 | 手动点击页面提供的“打开悬浮提示窗”链接 |
| 只有一台电脑 | 使用本地录音工具直接录 BlackHole 输出 | 将声音对比与会议助手分段录制后剪接 |

## 六、单机录制 BlackHole 的备用检查

如果没有第二台设备，可先列出 macOS 音频设备：

```bash
ffmpeg -f avfoundation -list_devices true -i ""
```

确认 BlackHole 的音频编号后，再用本机录音工具或 FFmpeg 录制其输出。正式录制前先录 5 秒并回放，确认录到的不是物理麦克风。设备编号以本机当次列表为准，不要照抄其他电脑的编号。
