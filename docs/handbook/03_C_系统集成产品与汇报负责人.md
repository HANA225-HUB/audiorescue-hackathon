# C：系统集成、产品与汇报负责人

## 1. 职责

C 负责公共 schema、pipeline 入口、A/B 契约、任务路由、冻结、组合验收、回滚和公开表达。C 不替代 A/B 重跑其可独立完成的实现，也不在缺少授权时扩大文件范围。

## 2. 单一入口

应用通过 `core.pipeline.process_audio` 处理一次任务。C 负责保证：

- 参数有界且语义稳定；
- 每个 job 使用隔离目录；
- A 的产物满足 schema；
- B 只消费公开结果；
- 未知异常转为可渲染的 failed 结果。

## 3. ProcessResult 三态

- `success`：核心音频、状态和允许展示的结果完整。
- `partial`：仍有可用结果，但转写、图表或交付的一部分失败。
- `failed`：没有可安全交付的核心结果。

状态必须由产物完整性推导，不能只依据调用是否返回。播放器、图片、文本或下载入口缺失时，界面必须同步降级。

## 4. 集成顺序

1. 校验输入与配置。
2. 创建隔离 job 路径。
3. 标准化音频。
4. 运行增强并验证两条输出轨。
5. 运行处理前/后转写。
6. 计算允许的指标与文本差异。
7. 生成波形、频谱和可选事件。
8. 固化安全结果并交给 UI。
9. 注册不透明本地交付地址。

任何阶段都不得通过原始异常、绝对路径或自由文本泄漏内部信息。

## 5. 路由与所有权

每个任务必须有唯一 `dispatch_id`，并写明：

- 目标角色；
- 精确允许文件；
- 验收命令；
- 禁止项；
- BLOCKED 与回滚条件。

C 对 CLAIM、CHECKPOINT、HANDOFF 和 BLOCKED 去重。两个角色可能修改同一文件时，先冻结旧任务或明确 SUPERSEDED，再创建新任务。

## 6. 契约验收

C 必须检查：

- 函数签名与配置键一致；
- `ProcessResult`、`TranscriptResult` 和告警字段完整；
- 数字有限、状态 fail-closed；
- 原始结果不会被 presenter 原地修改；
- 文件 URL 与 registry 的身份、摘要和结构验证一致；
- 缺失产物会清 URL、移除入口并降级。

## 7. 测试门禁

冻结前至少包含：

- 定向单元测试；
- 全量测试发现；
- `py_compile` 与 `git diff --check`；
- repo safety 与全公开文档隐私扫描；
- 固定 heads 的无冲突组合；
- 浏览器首屏、无横向滚动、无外联请求；
- 正常本地媒体的 HEAD/GET/Range；
- UI→core schema 与降级语义。

真实模型 smoke、synthetic/fixture 和用户效果测试必须分别报告。

## 8. 冻结

冻结评论应包含精确 head、测试状态、已知 P2 和失效条件。只要 head 变化，旧冻结立即失效并重新审查。

CI 全绿不能替代：

- 隐私审查；
- 对抗性边界测试；
- 跨模块契约检查；
- 组合树验证；
- 用户效果验收。

## 9. 合并与回滚

- 不自动合并。
- 不强制推送或改写历史。
- 按依赖顺序合并，文档隐私修复最后覆盖旧公开内容。
- 合并前在一次性工作树重做组合验收。
- 回滚按相反顺序进行，并保留稳定 schema 与隐私修复。

## 10. 公开汇报

只公开：

- 产品问题、架构和流程；
- 版本或指纹前缀；
- 测试数量、通过状态和有界耗时；
- 固定错误码、脱敏风险与回滚说明；
- fixture、模型 smoke 与用户测试之间的证据边界。

不得公开：

- 真实素材或正文；
- 成员、样例或内部评测映射；
- 原始日志、完整异常、路径、模型位置、缓存布局或凭据；
- 未经验证的效果或速度承诺。

## 11. 最终交付

C 向用户交付：

1. 固定测试版本或组合 heads。
2. 启动与回滚步骤。
3. 已通过门禁和仍待用户完成的效果测试。
4. 未决历史处理事项。
5. 明确的合并顺序；未经用户确认不执行最终合并。
