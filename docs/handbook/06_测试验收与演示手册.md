# “听清又听懂·智能音频急救台”测试、验收与演示手册

> 用途：把“代码能跑”推进到“结果可信、演示稳定、失败可退”。
> 适用版本：团队总技术手册 v1.0。
> 测试负责人：C 汇总；A 对音频输出负责；B 对页面与可视化负责；每个功能的编写者对其最小测试负责。

## 0. 一页验收结论

### 0.1 主链路发布门槛

正式主演示必须同时满足：

- 样例 A 连续三次从点击到完整结果成功；
- 样例 A 的增强音频可播放、无 NaN/Inf、无明显新增削波；
- 原始和增强两轨使用同一 Whisper 配置；
- 样例 A 有人工参考台词，`CER_after < CER_before`；若实测不成立，不得把它选为“转写改善”的主演示样例；
- 三人盲听中至少两人认为增强后更容易听清，且没有不可接受的水声、断字或金属失真；
- 对照图使用相同时间轴、幅度范围、STFT 参数和色标；
- 10–15 秒样例的总处理时间目标 ≤20 秒，允许的演示硬上限 ≤30 秒；
- 断网、应用重启、模型预热后可以完整处理；
- 5 分钟台本连续通过三次；
- 主程序失败时，20 秒内能切换到本地录屏。

如果其中任意一项不满足，必须降级、换已验证样例或修改演示表述；禁止靠隐藏失败结果过关。

### 0.2 P1 发布门槛

CLAP 环境事件只有满足以下条件才进入页面：

- 默认关闭，不影响 P0 启动时间；
- 只读取原始轨；
- 固定候选标签，样例 C 上目标事件能在正确时间窗稳定出现；
- 连续三次结果没有明显抖动；
- 阈值来自样例实测，不凭感觉填写；
- 误报可解释，页面明确写“模型推测”；
- 7 月 15 日 18:00 前未全部通过，整项删除。

### 0.3 质量判断顺序

```text
程序正确性
→ 输出音频安全性
→ 人耳可懂度与自然度
→ 转写任务收益
→ 可视化公平性
→ 性能与稳定性
→ 演示表达
```

声谱图变“干净”不能跳过人耳和转写证据，处理速度快也不能弥补音频更差。

## 4. 音频质量验收

### 4.1 数值安全检查

每次增强后自动检查：

```python
assert samples.size > 0
assert np.isfinite(samples).all()
assert np.max(np.abs(samples)) <= 1.0 + tolerance
assert duration_seconds > 0
```

建议报告以下值，但不将其当作“质量评分”：

- 输入/输出时长；
- 采样率、声道；
- 峰值绝对值；
- 削波样本比例；
- RMS 或响度估计；
- 处理实时率 `RTF = processing_time / audio_duration`。

### 4.2 A/B 音量公平

“增强轨更响”很容易被误听成“更清晰”。最终 A/B 必须记录统一的播放响度策略，二选一并固定：

1. 如果团队已经稳定接入响度测量，按同一目标响度匹配，并设置最大增益限制；
2. 如果不增加新依赖，至少固定系统音量和播放器音量，报告两轨 RMS/峰值，人工确认没有明显响度偏置。

不要在最后半天为了响度匹配引入一套不熟悉的新库。若做增益匹配，匹配只用于公平播放，不覆盖原始模型输出；保留未经匹配的增强文件供检查。

### 4.3 三人盲听表

由一人随机将两轨命名为 X/Y，另外两人先听；随后轮换，避免所有人都知道答案。

| 样例 | 评审人 | X 可懂度 1–5 | Y 可懂度 1–5 | X 自然度 1–5 | Y 自然度 1–5 | 噪声更少 | 异常伪影 | 总体选择 |
|---|---|---:|---:|---:|---:|---|---|---|
| A | A/B/C |  |  |  |  |  |  |  |
| B | A/B/C |  |  |  |  |  |  |  |
| CLEAN | A/B/C |  |  |  |  |  |  |  |

通过规则：

- 主样例 A 至少 2/3 选择增强轨；
- 可懂度中位数至少不下降，目标提升 ≥1 分；
- 没有 2/3 同时报告严重断字、水声或金属音；
- 干净语音不能被明显破坏；若强力模式破坏而标准模式稳定，则主演示锁定标准模式。

### 4.4 失败样例的处理

如果增强后听感或 CER 变差：

1. 先检查两轨是否确实使用同一句、同长度、同 ASR 配置；
2. 检查是否发生重采样、延迟错位、削波或响度偏差；
3. 从强力降到标准/轻度；
4. 检查 DeepFilterNet 的长度/延迟补偿；
5. 将该样例降为“能力边界”，不要继续当主演示证据；
6. 若所有样例都变差，停止做 UI 美化，回到增强管线排错。

不得手工修改转写文本后冒充模型结果。

## 5. 转写与 CER 验收

### 5.1 公平比较条件

原始/增强两轨必须：

- 使用同一 Whisper 模型；
- 使用同一语言参数；
- 使用同一解码参数；
- 使用对应的完整音频，不剪掉某一轨困难片段；
- 在同一环境中运行；
- 参考台词来自人工原稿，而非两次 Whisper 输出之一。

### 5.2 中文文本规范化

比赛前锁定且写进代码/报告，例如：

- Unicode 统一；
- 删除约定范围的标点；
- 删除无语义空格；
- 英文字母大小写统一；
- 数字保留原形式，不临时为了降低 CER 改写；
- 口头语是否保留，以原始参考台词为准。

所有样例使用同一规则。报告同时保留原文本和规范化文本，便于解释。

```text
变化：下降 xx.x 个百分点
```

不要把“下降 10 个百分点”写成“准确率提高 10%”，两者含义不同。参考文本很短时，单个字符就可能造成大幅波动，应同时显示字符数和实际差异。

### 5.4 无参考台词时

只允许显示：

- 原始轨转写；
- 增强轨转写；
- 字符级/词级差异；
- “以下差异不代表哪一版一定正确”的提示。

不允许显示自动生成的“正确率”“提升率”或让大语言模型判定哪段一定更真实。

## 9. 五分钟演示运行手册

### 9.1 上台前 15 分钟

由现场操作人 B 执行，C 复核：

- 接电源，关闭自动锁屏和系统更新；
- 开启勿扰模式，关闭消息通知；
- 关闭不相关窗口、终端历史和私人标签页；
- 固定系统音量与浏览器音量，接好扬声器；
- 关闭 Wi-Fi后确认本地链路；若比赛必须联网投屏，至少确认应用不依赖网络；
- 启动应用，观察无报错；
- 运行一次预热，不把预热结果当正式演示；
- 将页面回到初始状态，选择样例 A；
- 打开 PPT、本地录屏和备用静态结果页；
- 确认录屏有声音；
- 手机计时器准备好；
- 操作人和主讲人确认切换口令：“进入备用演示”。

### 9.2 推荐角色

| 人 | 台上职责 | 禁止事项 |
|---|---|---|
| A | 讲增强方法、音频公平性、边界；必要时回答模型问题 | 不临时调参数 |
| B | 操作页面、控制播放、切录屏 | 不边操作边长篇解释 |
| C | 主讲产品、证据闭环、Vibe Coding、收束 | 不承诺未实现功能 |

如果只能一人主讲，C 主讲，B 只操作，A 在问答补充。

### 9.3 逐秒台本

#### 0:00–0:30：问题与钩子

页面停留在输入区，C 说：

> “很多课堂、会议和采访录音不是完全没声音，而是人勉强听得到，却听不清、整理不出来。我们做的是一台智能音频急救台：让录音变清楚，也用处理前后的转写证明机器是否真的听懂得更好。”

B 播放原始音频 3–5 秒。不要播完整段，避免耗时。

#### 0:30–0:55：产品路径

C 指向四步：

> “流程只有四步：体检、增强、理解、证据。今天展示的是录制后准实时处理，我们没有把它包装成尚未完成的流式实时系统。”

#### 0:55–1:15：启动 Live Demo

B 展示已选中的样例 A 和“标准增强”，点击“开始急救”。

C 在等待期间说：

> “系统先统一采样格式并检查削波、静音等问题，再用 DeepFilterNet 增强人声；同一个 Whisper 配置分别转写处理前后两轨，保证比较公平。”

如果 20 秒仍无结果，B 看状态；30 秒硬上限到达则执行第 10 节切换，不继续沉默等待。

#### 1:15–2:10：A/B 听感

B 先播放原始轨 5–7 秒，再播放增强轨同一位置 5–7 秒。

A 说：

> “我们保留原始轨和完整增强轨，再用固定 dry/wet 强度得到实际播放结果。这样可以在去噪和自然度之间做可回退的选择。两轨采用同一播放设置，避免把更响误当成更好。”

不要反复播放；若现场音响表现不佳，说明耳机测试与报告数据，然后继续任务证据。

#### 2:10–2:55：转写与 CER

C 指向前后文本和差异：

> “这里只把转写变化当作任务证据。这个样例有团队事先锁定的真实台词，所以可以计算 CER；没有参考台词时，我们只展示差异，不会伪造准确率。”

读出最终实测的 Before/After CER 和“下降多少个百分点”。不要照搬开发期数字。

#### 2:55–3:25：视觉与工程证据

B 展开对照图与耗时。

A 说：

> “两张图使用完全相同的时间轴、频谱参数和色标。声谱变化只帮助解释模型做了什么，质量结论仍以人耳和转写为准。页面同时记录每个阶段的真实耗时与警告。”

#### 3:25–4:10：为什么不是简单模型串联

C 说：

> “预训练模型不是我们的自研成果。我们的工作是把它们做成一条可验证、可失败、可回退的产品链路：双轨公平转写、有真值才算 CER、重要环境声只从原始轨判断，以及任一非核心模块失败时仍能给出部分结果。”

如果 CLAP 已通过，展示样例 C 的一张结果图或快速切换缓存，不要再跑一个长 Live 任务：

> “在加分模式中，我们从原始轨检测警报等事件，因为强降噪可能把关键环境声一起抹掉。”

CLAP 未通过则完全不提页面功能，只可在未来工作中一句带过。

#### 4:10–4:40：Vibe Coding 过程

C 展示一页真实迭代：

1. AI 第一版提出/生成了什么；
2. 团队在真实音频上发现什么问题；
3. 人如何测试、否决或修正；
4. 最终增加了哪个回归测试。

推荐选择最有证据的一例：模型重复加载导致慢、两图色标不一致、强降噪导致断字、错误导致整页崩溃。必须是真实发生并保留记录的事件。

#### 4:40–5:00：收束

C 说：

> “我们不是用模型数量制造复杂度，而是把听感、视觉、可懂度和工程记录组成一个可信的音频急救闭环。它能帮助用户更快判断：这段录音是否真的被救回来，以及哪些信息仍不能忽略。”

立即结束，不在最后 20 秒打开新页面。

### 9.4 投影可读性

- 核心字号至少让后排看清；
- 页面只保留 1 个主行动按钮；
- 原始＝灰/橙、增强＝蓝/绿，全文一致；
- Before/After 标签同时写中文，避免只靠颜色区分；
- CER、总耗时是大号数字，但旁边写清条件；
- 工程日志、模型版本放折叠区，不占主演示首屏；
- 演示浏览器缩放在彩排中锁定。

## 10. 现场故障切换卡

### 10.1 切换优先级

```text
Live 完整结果
→ 固定样例本地缓存
→ 预生成静态结果页/截图
→ 本地录屏
```

故障发生后不在台上调代码、重装包、下载权重或换模型。

### 10.2 处理超时

触发：点击后 30 秒仍无完整结果。

B：停止继续等待，打开固定样例缓存结果或录屏。
C：说：

> “现场推理超出我们设定的 30 秒演示门槛，我们切换到同一版本、同一配置预先完整运行并记录的结果，继续展示证据链。”

随后按 A/B、转写、图继续，不编造这次任务已成功。

### 10.3 页面崩溃

触发：白屏、服务退出、播放器不可用。

- B 只尝试一次已验证的刷新；
- 5 秒内未恢复，直接打开本地录屏；
- C 用一句话说明切换，不展开报错细节；
- A 准备在录屏播放时解释管线与质量验证。

### 10.4 没有声音

顺序检查，最多 15 秒：

1. 系统是否静音；
2. 浏览器标签是否静音；
3. 输出设备是否正确；
4. 仍无声则直接播放带声音录屏；
5. 若场地音响本身故障，展示波形、转写和测试报告，不把问题归因于模型。

### 10.5 增强效果现场不明显

- 不临时切强力模式；
- 指向同样例的盲听记录和 CER；
- 说明场地扬声器会影响细节；
- 如允许，评委可会后戴耳机听；
- 不夸张声称“噪声全部消失”。

### 10.6 转写增强后更差

如果页面临时重算得到 `CER_after ≥ CER_before`：

- 不隐藏；
- C 说：“这个结果说明增强并不对所有样例都稳定有益，我们把失败也保留下来”；
- 切到已锁定且通过验收的主演示结果；
- 解释 dry/wet 与边界样例，而不是手改文本。

主演示在冻结后应使用固定样例和固定配置，此故障通常意味着样例、环境、缓存或代码已发生漂移，赛后再排查。

### 10.7 网络故障

正常设计下不应影响主链路。若页面引用网络资源导致异常：

- 切本地录屏；
- 不能现场开热点下载模型；
- 答辩如被问到，坦诚说明原型的离线测试结果与此次页面资源问题。

## 11. 答辩问答验收

三人互问，答案保持一致。

### Q1：“这不就是把几个预训练模型串起来吗？”

答题要点：

- 明确 DeepFilterNet、Whisper、CLAP 是预训练模型；
- 团队贡献是产品定义、统一管线、双轨公平评估、真实 CER、原始轨事件保护、错误隔离、缓存和断网交付；
- 展示真实测试与失败样例，而非声称算法原创。

### Q2：“为什么说智能？为什么不是普通降噪？”

- 不只输出增强音频；
- 同时理解语音、比较任务结果、可选识别原始环境事件；
- 通过结果契约与警告告诉用户哪里可信、哪里未知。

### Q3：“如何证明更好？”

- 公平 A/B；
- 三人盲听；
- 同模型双轨转写；
- 有真值时的 CER；
- 没有干净参考时不伪造 PESQ/STOI；
- 声谱图只作解释。

### Q4：“为什么不是实时？”

- 当前完成的是录制后准实时；
- 真实流式涉及分块、状态、音频设备、端到端延迟与回声问题；
- 两天内优先把可测量、可回放、可比较的链路做稳；
- 不把未来计划说成已完成。

### Q5：“增强会不会删掉警报？”

- 有可能，因此 P1 事件理解只读取原始轨；
- 页面不能用增强轨“证明”关键声音不存在；
- 事件标签是模型推测，不代替安全系统。

### Q6：“为什么用 Whisper 前后比较，它自己也会错？”

- 正因会错，所以同一模型同一配置做受控对照；
- 有真实台词时才计算 CER；
- 无真值时只展示差异；
- 它是任务证据之一，不是唯一质量结论。

### Q7：“AI 在开发中做了什么？”

- 用真实 `AI_USAGE.md` 回答：选型、脚手架、接口、测试、错误定位、UI；
- 人类定义需求、听真实输出、做盲测、验证指标、拒绝不可靠建议、决定冻结；
- 展示一个具体错误→测试→修正闭环。

### Q8：“用户音频会上传吗？”

- 若最终版全本地：明确本机处理和本地输出；
- 若任何环节上云：必须如实说明服务、数据流向和删除方式；
- 不回答一个与实际架构不一致的“不会”。

### Q9：“能处理多长音频？”

- 回答页面已验证上限，而非理论无限；
- 主演示为 10–15 秒，两天原型优先短录音闭环；
- 长音频需要分段、进度、内存和持久化，是后续工程工作。

### Q10：“你们最重要的取舍是什么？”

- 放弃流式、多模型和硬件；
- 先实现一个离线稳定、可验证的闭环；
- CLAP 是可拆 P1，不让加分项拖垮主功能。
