# 05｜AI 协作提示词与交接模板

> 用途：让三个人的三个 AI 客户端像一支工程团队，而不是三个同时改代码的随机生成器。
> 核心原则：**人定目标和验收，AI 做受限任务；一次只改一小块，真实运行后再继续。**

---

## 1. 模型与人的分工

| 成员 | 默认客户端 | 最适合投入 | 不应单独决定 |
|---|---|---|---|
| A | 比赛方 GPT-5.5，近乎无限额度 | 环境报错、音频 I/O、DeepFilterNet、Whisper、边界测试的高频闭环 | 听感是否变好、公共 schema、产品声明 |
| B | 比赛方 GPT-5.5，近乎无限额度 | Gradio、状态组件、可视化、CSS、小步截图与回归 | 模型调用、CER 口径、公共 schema |
| C | 官方 GPT Pro / GPT-5.6 Sol | 架构、契约、跨模块诊断、Code Review、集成、发布审查、叙事 | 仅凭模型描述判断音质 |

官方模型资料显示 GPT-5.5 与 GPT-5.6 Sol 都适合编码和专业工作；GPT-5.6 Sol 更适合复杂全局任务，但比赛方安装版与官方客户端的工具、上下文和执行权限可能不同。人的经验和客户端实测优先于型号。

两类模型都不应被当作“听音评委”。官方 API 模型页列出的直接输入是文本/图像而非音频。实际客户端即使允许上传音频，也可能先做不可见的转写或预处理。最终 A/B 听感、失真和自然度由三名成员亲自验证。

## 2. 开工前 20 分钟客户端快测

三个人使用同一份小任务，不动正式代码：

1. 实现一个“校验 strength 必须在 0–1”的纯函数及 4 个测试；
2. 给出一个已知 Python traceback，让客户端定位根因；
3. 给出 30 行 diff，让客户端找回归风险；
4. 记录是否能读文件、改文件、运行命令/测试、看到完整报错；
5. 记录首次可运行结果所需时间、错误次数和是否越权改文件。

快测表：

| 人/客户端 | 可读文件 | 可改文件 | 可运行测试 | 首次通过用时 | 越权改动 | 适合任务 |
|---|---|---|---|---:|---|---|
| A / GPT-5.5 |  |  |  |  |  |  |
| B / GPT-5.5 |  |  |  |  |  |  |
| C / GPT-5.6 Sol |  |  |  |  |  |  |

若某客户端不能实际执行命令，就让它只负责生成补丁建议和测试方案，由人运行；不要把“它说测试通过”当作证据。

## 3. 所有 AI 会话共同的上下文

每个新会话先粘贴或让 AI 阅读下面内容：

```text
项目：听清又听懂·智能音频急救台
比赛：当前两天 Vibe Coding 黑客松，不考虑其他比赛复用
P0：上传/录制短噪声音频→DeepFilterNet增强→原轨和增强轨同配置Whisper转写→A/B、同尺度声谱图、文本差异
P1：CLAP从原始轨做固定环境事件标签；只有P0稳定后才可做
不是：不训练模型、不做多麦阵列、不做真实流式、不做账号/数据库、不把缓存伪装成新推理
唯一入口：process_audio(...) -> ProcessResult
公共契约：core/schemas.py
文件所有权：A=audio_io/diagnostics/enhance/transcribe；B=app/ui/visualize；C=schemas/pipeline/metrics/cache/events/config/docs
状态：增强成功且ASR/图失败可partial；输入或增强失败为failed；CLAP失败不影响P0
截止：7月15日11:30 P0；18:00 CLAP Go/No-Go；7月16日10:00停止新功能，14:00冻结
规则：只修改本任务授权文件；不得虚构API/测试/耗时；修改后运行最小测试并报告真实输出。
```

正式仓库应把这段内容写入 `PROJECT_GUIDE.md`。任何一次架构决定变化，先更新该文件，再开新 AI 任务。

## 4. 单任务卡：每次提示词的前半段

不要发“帮我把整个项目做完”。复制以下模板：

```text
[单任务卡]
角色：A / B / C
目标：<一个动词开头、一次可完成的目标>
授权修改：<准确文件列表>
只读参考：<准确文件列表>
输入：<样例/函数/错误/截图>
期望输出：<文件、字段、页面状态>
验收命令：<至少一条>
必须保持：<契约/行为>
禁止：<越权文件、新依赖、换框架等>
停止条件：<何时不要继续试>

先复述约束并给出不超过5步的最小计划；确认现有实现和已安装版本后再修改。
完成后只汇报：修改文件、运行命令、真实结果、剩余风险、回滚方法。
```

好任务示例：

```text
目标：让 core/transcribe.py 在一轨失败时返回可诊断错误，且不影响另一轨调用。
授权修改：core/transcribe.py、tests/test_transcribe.py
验收：pytest -q tests/test_transcribe.py
禁止：修改 schemas.py、pipeline.py、升级 Whisper。
```

坏任务示例：

```text
把后端、页面、模型、测试和部署全部完善一下，做得高级一点。
```

## 5. 实现提示词

### 5.1 通用小功能

```text
阅读 PROJECT_GUIDE.md、core/schemas.py 和本任务涉及的现有文件。
本次只实现：<功能>。
授权文件：<列表>。不要修改其他文件，不要新增依赖，除非先证明现有依赖做不到。
先检查当前函数、调用者和测试，避免重复实现或改变公共接口。
实现最小版本，并补充：正常输入、边界输入、失败路径各至少一个测试。
运行测试和一个真实 smoke test。不要只做语法检查。
若第三方 API 不确定，先检查已安装版本、官方文档或对象签名，不要猜函数名。
```

### 5.2 A：音频后端

```text
你只拥有 core/audio_io.py、diagnostics.py、enhance.py、transcribe.py 及对应测试。
目标：<例如：封装DeepFilterNet并生成可播放enhanced_full和enhanced_mix>。
必须遵守 48kHz/单声道标准路径、模型单例、延迟/长度对齐、dry-wet、NaN/Inf和峰值检查。
不得修改 core/schemas.py 或 pipeline.py，不得把 shell 文本解析作为正式接口。
真实跑一段10秒样例，报告输入/输出时长、峰值、处理耗时和听感仍需人工检查的事项。
```

### 5.3 B：UI 与可视化

```text
你只拥有 app.py、ui/*、core/visualize.py、core/text_diff.py 及对应测试。
先用固定 ProcessResult fixture 开发，不等待模型。
页面必须覆盖 success、partial_asr、failed_enhance、input_error、cache 五种状态。
前后图使用相同时间轴、频率轴、STFT参数和dB色标；UI不加载模型、不自行计算CER。
在1366×768视窗截图检查首屏；处理期间按钮禁用并显示阶段。
```

### 5.4 C：集成

```text
你只拥有 schemas.py、pipeline.py、metrics.py、cache.py、events.py、configs和集成测试。
把 A/B 的现有接口组装为 process_audio，不复制它们的实现。
先列每个阶段的输入/输出和异常，再修改。
增强失败必须failed；ASR或图失败可partial；CLAP失败只警告。
每个任务使用独立job_id，写result.json和分阶段耗时；缓存命中必须可见。
运行单元测试、pipeline集成测试和一个真实端到端样例。
```

## 6. Debug 提示词

### 6.1 先诊断、再最小修复

```text
这是可重复问题，不要先重构。
环境：<OS/Python/包版本/设备>
复现命令：<命令>
期望：<结果>
实际：<结果>
完整精简报错：<traceback>
最近成功版本：<提交>
最近改动：<diff或文件>

请先给最多3个互相可区分的根因假设，每个给一条验证方法。
指出最先违反契约的位置，不要只解释最后一行报错。
只在授权文件内做最小修复；不要吞异常、删除测试、降级契约或升级整个环境。
修复后重跑原失败用例和相关回归，并贴真实结果摘要。
```

### 6.2 安装/版本错误

```text
不要给通用“重装所有依赖”方案。先读取：python -V、which python、pip -V、pip check、相关包版本、平台架构、磁盘余量和完整安装错误。
区分：错误Python环境、缺少系统依赖、无对应wheel、PyTorch冲突、模型下载失败、磁盘不足。
按风险从低到高给验证步骤；任何卸载、全量升级或清缓存动作都先停下来由人确认。
```

本机已知事实：默认 `python3` 是 Miniforge Python 3.13.12，不用于项目；应显式使用 `/opt/homebrew/opt/python@3.10/bin/python3.10` 创建 `.venv`；FFmpeg 当前需要安装。

## 7. Code Review 提示词

### 7.1 模块 review

```text
以严格审查员身份审查下面diff，不写新功能。
项目契约见 PROJECT_GUIDE.md 和 core/schemas.py。
按严重性列问题：P0阻断、错误结果/数据串线、隐私/安全、性能、可维护性。
每个问题必须给文件/位置、触发条件、用户影响和最小修复；没有证据就不要报。
重点检查：模型重复加载、路径覆盖、异常被吞、缓存键缺字段、前后ASR配置不同、图像尺度不一致、缓存冒充新推理。
最后列出仍需人完成的听感/投影/断网检查。
```

### 7.2 冻结前全仓审查（交给 C 的 GPT-5.6 Sol）

```text
阅读目录树、PROJECT_GUIDE、当前diff、测试输出、TEST_REPORT和演示台本。
目标不是改得更漂亮，而是判断是否能在明天现场稳定演示。
只找：会阻断启动、会返回错误证据、会依赖网络、会暴露隐私、会让答辩声明失真的问题。
禁止建议新增框架、模型、数据库、动画或重构。
按“必须修/可接受已知限制/赛后再做”分类，并给最小回归集。
```

## 8. 测试生成提示词

```text
不修改生产代码。根据现有契约，为<模块>设计最小但高价值的测试。
单元测试默认不下载模型，用stub/mock验证编排；真实模型放在显式smoke脚本中。
至少覆盖：正常、空/损坏、边界长度、异常、重复运行、输出路径隔离。
测试不能只assert不报错；要检查字段、文件存在/可读、状态、警告码和缓存标记。
先说明每个测试防止什么真实故障，再实现并运行。
```

测试失败时禁止让 AI 为了绿灯删断言或把异常路径改成无条件成功。

## 9. 第三方 API 防幻觉提示

DeepFilterNet、Whisper、Gradio 和 PyTorch 的版本会影响 API。每次让 AI 接第三方库时增加：

```text
不要凭记忆猜API。先检查本环境安装版本、官方README、函数签名或最小import实验。
把确认过的调用方式和版本写入交接记录。
若官方示例与当前版本不一致，保留完整错误并提出最小适配，不要换一整套库。
```

AI 输出中的以下表述一律要求证据：

- “已经测试通过”；
- “支持 macOS/MPS/CUDA”；
- “实时/低延迟”；
- “准确率提升”；
- “这是官方参数”；
- “这个模型一定比另一个好”。

## 12. AI 使用证据模板

比赛强调 Vibe Coding，不要只展示聊天截图。`AI_USAGE.md` 每条记录：

```text
时间：
成员/模型/客户端：
开发目标：
给AI的关键约束：
AI提出或生成：
人如何验证：
结果：接受 / 修改后接受 / 否决
发现的问题：
最终改动与测试：
证据：提交、日志、截图或测试报告位置
```

最终答辩选三条真实故事，优先：

1. AI 初版重复加载模型，团队通过耗时测试发现并修复；
2. AI 给两张声谱图用了不同色标，团队通过公平性审查否决；
3. 强降噪让转写变差，团队降低 dry/wet 并保留失败边界；
4. 一个可选模块异常拖垮整页，团队通过 `partial`/warning 隔离；
5. AI 建议更换大模型，团队用两天完成率和实测拒绝。

必须用真实发生的事件，不要预先编造“迭代故事”。

## 13. Git 与并行协作规则

- A/B 各自在自己的分支或独立小提交工作；C 维护可演示主分支；
- 每个提交只对应一个可说清的任务；
- 合并前必须有测试命令和交接记录；
- 公共 schema、依赖文件和启动入口由 C 统一合并；
- 同一文件只有一名当前所有者；
- 合并冲突由人阅读语义解决，不把两个版本整段拼在一起；
- 每完成一个稳定门槛保存可回退版本；
- 7 月 16 日 10:00 后不接受“顺便重构”。

推荐提交信息：

```text
feat(enhance): add dry-wet mix and output guards
feat(ui): render partial asr state
fix(pipeline): isolate optional event failure
test(audio-io): cover silent and corrupted files
docs(demo): lock five-minute script
```

## 14. 隐私与安全

- 不把真实私人会议、采访或课堂录音上传给第三方 AI；
- 提示词中用最小日志，去掉密钥、Token、私人路径和身份信息；
- `.env`、SSH 密钥、平台凭据不进聊天和 Git；
- AI 提出的删除、清缓存、卸载、开放公网端口动作必须由人审查；
- 远端只上传自录或授权样例；
- 页面和日志不显示本机私人绝对路径；
- 不让 AI 自动删除这台磁盘紧张的 Mac 上的任何用户文件。

## 15. 每个任务的完成检查

在接受 AI 结果前逐项回答：

- [ ] 它只改了授权文件吗？
- [ ] 它是否确认了当前版本/API，而不是凭记忆？
- [ ] 真实运行了什么命令？
- [ ] 结果中有无测试、样例和耗时证据？
- [ ] 有没有吞异常、写死路径或覆盖输出？
- [ ] 有没有改变公共契约却未通知？
- [ ] 有没有引入不必要依赖或网络调用？
- [ ] 对音频质量的结论是否仍需人耳验证？
- [ ] 失败时能否回滚？
- [ ] 是否更新交接与 AI_USAGE？

任何一项答不出来，就不能把该任务标成完成。

## 16. 两天内的 AI 节奏

### 7 月 14 日晚

- 每人只开一个主会话对应自己的模块；
- 先读项目指南，再做客户端快测；
- 用 GPT-5.5 高频完成 A/B 独立模块；
- 用 GPT-5.6 Sol 冻结 schema、检查接口冲突；
- 90 分钟内集成，不让 AI 无限规划。

### 7 月 15 日

- 上午只用 AI 修 P0 和补测试；
- 下午用 AI 汇总日志、生成图表代码和审查 CLAP 沙盒；
- 18:00 后停止问“还能加什么”，改问“什么会在现场坏”；
- 晚上让 GPT-5.6 Sol 做全仓发布审查，但任何修复仍按文件所有权分发。

### 7 月 16 日

- 10:00 后提示词必须包含“禁止新增功能”；
- 14:00 后只处理阻断性缺陷；
- 不让 AI 升级依赖、换模型、清缓存或重写页面；
- AI 用于检查清单、问答模拟和文字核对，不再制造大 diff。

## 17. 停止规则

出现以下任一情况，停止当前 AI 循环并由人/C 决策：

- 连续两次修复产生同一错误；
- AI 开始跨越文件所有权；
- 建议全量升级/重装/换框架；
- 一个小问题改动超过三个生产文件；
- 测试通过但真实音频失败；
- 输出依赖现场网络；
- 修改会破坏已锁定演示版本；
- 已到冻结时间。

最后一句团队口令：

> AI 的输出不是完成证明；可复现命令、真实结果、人耳验证和可回退版本才是。

## 19. GitHub Issue 总线协议

当 A/B/C 各自使用独立 Codex 客户端时，统一用一个 GitHub Issue 做消息总线。总线只负责派单、领取、心跳、检查点和交接；不要把它变成聊天记录、密钥仓库或私有录音索引。

### 19.1 消息类型

| 标签 | 发送者 | 用途 | 行动规则 |
|---|---|---|---|
| `[ROUTER-HOLD]` | C 或人 | 冻结当前阶段，防止 AI 自行开工 | A/B/C 只能 ACK 或报告状态，不改代码、不推分支 |
| `[AGENT-ACK]` | A/B/C | 客户端接入确认 | 写清角色、可读/可写 Issue、当前分支和是否能定时监听 |
| `[DISPATCH]` | 人或 C 代人发布 | 唯一有效派单 | 必须包含 `dispatch_id`、目标角色、授权文件、禁止事项和验收命令 |
| `[CLAIM]` | 目标角色 | 领取派单 | 每个角色对每个 `dispatch_id` 只回复一次，先 CLAIM 再动手 |
| `[PING]` | C 或人 | 监听活性检查 | 必须带 `sequence`，目标角色只回对应 `[PONG]` |
| `[PONG]` | 目标角色 | PING 回执 | 同一 `sequence` 只回一次，不触发代码动作 |
| `[CHECKPOINT]` | 执行角色 | 阶段进展 | 每 90 分钟或阶段完成时发，列真实测试和阻塞 |
| `[HANDOFF]` | 执行角色 | 派单完成交接 | 列提交、PR、测试、证据边界、已知风险和回滚方式 |
| `[BLOCKED]` | 执行角色 | 无法继续 | 说明阻塞条件、已尝试验证、需要谁提供什么 |
| `[ROUTER-SUMMARY]` | C | 总线阶段总结 | 汇总 CLAIM/PONG/HANDOFF 状态，不替代各角色测试证据 |

没有明确 `[DISPATCH]` 且目标角色不匹配时，AI 只读 Issue 并安静报告“无本角色行动”。产品代码任务在 `[ROUTER-HOLD]` 下保持 HOLD，除非后续 `[DISPATCH]` 明确解除对应范围。

### 19.2 `dispatch_id`、`sequence` 与幂等

- `dispatch_id` 是派单唯一键，格式建议为 `AR-R<轮次>-<角色>-<序号>`，例如 `AR-R3-B-001`。
- `[PING]` 必须带 `sequence`，格式建议为 `<dispatch_id>-<角色>-PING-<两位序号>`。
- AI 看到已 CLAIM 的同一 `dispatch_id` 时，不重复 CLAIM；继续执行当前派单或只报告状态。
- AI 看到已 PONG 的同一 `sequence` 时，不重复 PONG；轮询重复读取 Issue 不能制造重复评论。
- `[CHECKPOINT]` 可重复，但每次必须有新增事实：完成阶段、测试输出、阻塞变化或风险更新。
- `[HANDOFF]` 每个 `dispatch_id` 只发一次。若后续需要修复，必须由新的 `[DISPATCH]` 派发。

### 19.3 定时监听规则

- 监听只读目标 Issue，不扫描私信、通知中心、其他仓库或本机私人目录。
- 默认轮询间隔为 5 分钟；时长必须在 ACK/CLAIM 中写清，到期后自动静默。
- 轮询期间若没有目标角色的 `[PING]` 或 `[DISPATCH]`，不要评论刷屏。
- 监听到新 `[DISPATCH]` 后，先校验目标角色、授权人、文件范围和禁止事项，再 `[CLAIM]`。
- 自动化过期、被手动停止或客户端能力不足时，用 `[BLOCKED]` 或下一次人工状态说明，不伪装仍在监听。

### 19.4 精确授权与角色所有权

每个 `[DISPATCH]` 必须写明：

- 目标角色和 GitHub 用户；
- 基线分支和当前 SHA；
- 允许修改文件的精确列表；
- 只读参考文件；
- 禁止修改范围；
- 必跑验收命令；
- 是否允许访问服务器、模型、网络和真实样例。

角色默认所有权：

- A：音频 I/O、诊断、增强、转写及对应测试；
- B：`app.py`、`ui/`、可视化、文本 diff、页面测试及浏览器证据；
- C：schema、pipeline、metrics、cache、events、configs、集成测试和总文档。

若问题落在别人文件里，本角色不越权修复；发 `[CHECKPOINT]` 或 `[BLOCKED]`，附最小复现和建议 owner。公共 schema、依赖、启动入口、比赛样例和合并策略默认由 C 或人统一派单。

### 19.5 PR、提交与合并边界

- A/B 在自己的功能分支提交；文档或协议类任务若派单要求独立 PR，必须从指定基线新建分支。
- 不重写历史、不 force-push、不自动合并、不关闭他人 PR。
- 一个派单内不得混入未授权文件；跨 PR 任务要分别提交、分别说明测试。
- PR 目标分支按派单执行，通常为 `codex/c-integration`。
- HANDOFF 必须列出分支、提交 SHA、PR 链接、修改文件、测试结果、证据边界、已知 warning、阻塞和回滚方式。
- C 负责最终整合和冲突语义判断；A/B 不把本地通过当作已集成。

### 19.6 禁止写入 Issue 或 PR 的内容

- SSH 密码、Token、API key、cookie、验证码、私钥；
- 私有录音、未授权文本、私人会议内容或可识别个人身份的原始数据；
- 本机或服务器私人绝对路径；
- S03、`locked_test` 的音频内容、听感比较、指标、截图或调参结论；
- 模型缓存、outputs、真实录音和大二进制文件；
- 未经确认的“真实推理成功”“效果提升”“公平对比”等结论。

可写入的证据应脱敏：提交 SHA、分支名、相对文件名、测试命令摘要、公开 fixture 名称、截图用途说明、错误类别和可复现步骤。

### 19.9 脱敏示例

A 的脱敏示例：

```text
[HANDOFF]
角色：A
dispatch_id：AR-R3-A-001
状态：完成
分支与提交：feat/a-round2-integration @ <sha>
PR：#<number>
修改文件：core/enhance.py、core/transcribe.py、scripts/smoke_audio_core.py、tests/test_enhance.py、tests/test_transcribe.py
测试：音频后端单元测试通过；真实 smoke 使用公开 dev fixture，未使用 S03/locked_test。
浏览器或真实运行证据：报告模型名、相对权重文件名、SHA-256、CUDA 是否可用、冷/热耗时；不包含服务器绝对路径。
fixture/真实边界：单元测试为 mock；smoke 为公开 fixture。
已知 warning：DeepFilterNet 上游弃用提醒，不影响本轮验收。
回滚方式：revert <sha>
```

```text
[HANDOFF]
角色：B
dispatch_id：AR-R3-B-001
状态：完成

fixture/真实边界：页面真实 pipeline 默认未改；视觉状态使用显式 fixture，不冒充模型推理。
```
