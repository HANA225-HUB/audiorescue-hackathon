# 05｜AI 协作提示词与交接模板

本手册用于在公开仓库内协调多名成员和多个 AI 客户端。它只记录公开安全的协作规则、派单格式和交接模板，不保存非公开素材、访问凭据、内部台账、外部环境信息或可识别个人的原始内容。

核心原则：

- 人决定目标、授权范围和验收标准；AI 只执行明确派单。
- 每次只处理一个小任务，先确认现状，再最小修改。
- Issue 只做公开协调总线，不做素材库、日志仓库或访问入口。
- 任何非公开信息只留在未跟踪的本地私有台账中，不进入 Issue、PR、提交或文档正文。
- 没有明确授权时，AI 只能只读观察并安静报告无行动。

---

## 1. 角色与边界

角色用于减少并行冲突。实际文件范围以每条 `[DISPATCH]` 为准，派单未列出的文件默认不可修改。

| 角色 | 主要职责 | 不应单独决定 |
|---|---|---|
| A | 音频后端、输入输出、增强与转写相关实现及测试 | 页面展示、公共契约、发布声明 |
| B | 页面、可视化、展示状态、前端测试与截图证据 | 后端模型调用、公共契约、最终合并 |
| C | 契约、集成、配置、总体验收、文档审查与发布协调 | 代替 A/B 完成其独占文件 |

共同规则：

- 只修改派单列出的文件。
- 只运行派单允许的命令。
- 不自动合并、不关闭他人 PR、不重写历史、不强制推送。
- 不访问未授权素材、外部环境、模型缓存或非公开台账。
- 不在公开渠道复述原始错误全文、原始输出、路径、凭据或内部细节。

## 2. 单任务卡

每次交给 AI 的任务都应缩小到一次可完成的改动。推荐模板：

```text
[单任务卡]
角色：A / B / C
目标：<一个动词开头、一次可完成的目标>
授权修改：
- <repo-relative-file>
只读参考：
- <repo-relative-file>
输入：<公开 fixture、合成样例、截图描述或脱敏错误类别>
期望输出：<字段、页面状态、文档段落或测试结果>
验收命令：
- <command>
必须保持：<公共契约、状态语义、兼容边界>
禁止：<越权文件、新依赖、外部访问、凭据、非公开素材>
停止条件：<何时固定脱敏 BLOCKED>

请先复述约束，检查当前实现，再给不超过 5 步的最小计划。
完成后只汇报：修改文件、运行命令、真实结果摘要、剩余风险、回滚方法。
```

好任务示例：

```text
目标：让页面在交付文件缺失时降级为 partial，并展示安全提示。
授权修改：
- ui/presenters.py
- tests/test_presenters.py
验收命令：
- python3 -m unittest tests.test_presenters -v
禁止：修改后端、公共契约、依赖或未授权文档。
```

坏任务示例：

```text
把后端、页面、测试和发布全部完善一下，做得高级一点。
```

## 3. 通用实现提示词

```text
阅读项目指南、公共契约和本任务涉及的现有文件。
本次只实现：<功能>。
授权文件：
- <file>

不要修改其他文件，不要新增依赖，除非派单明确允许。
先检查当前函数、调用者和测试，避免重复实现或改变公共接口。
实现最小版本，并补充正常、边界、失败路径测试。
运行派单列出的验收命令。
若第三方 API 不确定，先检查仓库固定依赖、对象签名或公开说明，不凭记忆猜函数名。
```

### A 侧任务提示

```text
你只处理派单授权的音频后端文件。
保持输入输出契约、状态语义和失败可诊断性。
单元测试默认使用 stub 或 mock；公开 smoke 只能使用授权公开样例或合成输入。
不要下载、替换或公开任何模型、素材、缓存或本地台账内容。
失败时给出安全错误类别，不输出路径、命令、堆栈或内部细节。
```

### B 侧任务提示

```text
你只处理派单授权的页面、可视化或文档文件。
页面必须区分 success、partial、failed，并用稳定 class 或 data attribute 表达状态。
用户可见的 error/warning 文本必须安全清洗，不能暴露路径、堆栈、命令、凭据或内部细节。
文件交付失败、关键音轨不可播放或关键结果缺失时，不能仍显示完整 success。
截图证据只证明布局和状态，不冒充模型效果。
```

### C 侧任务提示

```text
你只处理派单授权的契约、集成、配置、验收或总文档文件。
先列每个阶段的输入、输出、异常和状态，再修改。
不要复制 A/B 的实现到 C 文件。
公共契约变化必须在派单中明确授权，并通知受影响角色。
总体验收只报告公开安全摘要，不公开非公开素材、外部环境细节或原始输出。
```

## 4. Debug 提示词

```text
这是可重复问题，不要先重构。
环境：<公开可写的版本摘要>
复现命令：<仓库内验收命令>
期望：<结果>
实际：<安全错误类别和脱敏摘要>
最近成功版本：<commit sha>
最近改动：<repo-relative diff 摘要>

请先给最多 3 个互相可区分的根因假设，每个给一条验证方法。
指出最先违反契约的位置，不要只解释最后一个报错现象。
只在授权文件内做最小修复。
不要吞异常、删除测试、降低契约或改变未授权依赖。
修复后重跑原失败用例和相关回归，并贴真实结果摘要。
```

安装或环境问题只允许引用仓库固定依赖和公开 runbook。不得给出裸版本升级、整目录传输、外部环境初始化或隐式联网步骤。需要外部资源时，先固定脱敏 `[BLOCKED]`，等待新的授权。

## 5. Code Review 提示词

```text
以严格审查员身份审查下面 diff，不写新功能。
项目契约见公开指南和派单授权范围。
按严重性列问题：P0 阻断、错误结果、数据串线、隐私/安全、性能、可维护性。
每个问题必须给文件/位置、触发条件、用户影响和最小修复。
没有证据就不要报。
重点检查：
- 是否修改了未授权文件；
- 是否把失败伪装成成功；
- 是否暴露路径、堆栈、命令、凭据、原始输出或非公开素材；
- 是否引入不必要依赖、外部访问或隐藏状态；
- 是否破坏 success/partial/failed 契约；
- 是否缺少回归测试。
最后列出仍需人完成的主观体验、演示设备和发布口径检查。
```

冻结前审查只找会阻断启动、返回错误证据、依赖外部资源、暴露非公开信息或让答辩声明失真的问题。禁止建议新增框架、模型、账户体系或大重构。

## 6. 测试生成提示词

```text
不修改生产代码。根据现有契约，为 <module> 设计最小但高价值的测试。
单元测试默认不访问外部资源，用 stub/mock 验证编排。
至少覆盖：正常、空输入或损坏输入、边界长度、异常、重复运行、输出隔离。
测试不能只 assert 不报错；要检查字段、文件存在性、状态、警告码和缓存标记。
先说明每个测试防止什么真实故障，再实现并运行。
```

测试失败时禁止为了绿灯删除断言、吞异常、把错误路径改成无条件成功，或把未授权依赖加入项目。

## 7. 交接模板

```text
[HANDOFF]
role=A/B/C
dispatch_id=<id>
pr=#<number>
branch=<branch>
head=<full-sha>
status=READY_FOR_REVIEW / PARTIAL / BLOCKED
changed_files=<repo-relative files only>
implemented=<public summary, no raw outputs>
validation=<commands and pass counts>
ci=<check result or not_run reason>
known_risks=<safe summary or none>
rollback=<commit sha or revert plan>
privacy=PASS/FAIL
server_used=false/true-with-authorization
private_audio_used=false
force_push=false
auto_merge=false
```

交接不合格的典型句子：

- “应该能跑”；
- “AI 说没问题”；
- “我这边好了，你接一下”；
- “版本忘了，反正最新”；
- “报错你自己看看”。

交接只写公开安全证据：提交 SHA、PR 号、相对文件名、命令摘要、测试数量、CI 状态、截图用途和脱敏风险。不要写原始素材、完整异常、外部地址、访问凭据、本机路径或非公开台账内容。

## 8. 跨角色任务卡

发现问题在别人文件中时，不越权修改，发：

```text
[跨角色任务]
发现人：A/B/C
目标所有者：A/B/C
现象：<脱敏摘要>
最小复现：<公开命令或合成输入>
证据类别：<测试失败、状态错误、截图、契约不一致>
违反的契约：<公开规则>
期望行为：<一句话>
建议最小修改位置：<repo-relative file>
相关回归：<test name>
优先级：P0/P1/P2
```

阻断问题由 C 或人排序。A/B 的 AI 只改自己被授权的文件；公共契约、依赖、启动入口和合并策略默认等待明确派单。

## 9. Git 与并行协作规则

- 每个派单对应一个清晰提交或明确的无改动结论。
- 同一文件同一时间只有一个角色拥有写权限。
- 合并前必须有验收命令和交接记录。
- 冲突由人阅读语义解决，不把两个版本整段拼接。
- PR 目标分支、draft/ready 状态和合并策略以派单为准。
- 完成一个稳定门槛后保留可回退版本。
- 冻结后只处理阻断性缺陷。

推荐提交信息：

```text
fix(ui): sanitize display errors
fix(ui): downgrade incomplete delivery state
test(ui): cover partial delivery warnings
docs(bus): clarify issue handoff template
docs(runbook): remove unsafe public instructions
```

## 10. 隐私与安全

禁止写入 Issue、PR、提交或公开文档：

- 访问凭据、会话凭证、验证码、私钥或任何可复用授权材料；
- 非公开素材、原始文本、个人身份信息或未授权内容；
- 本机或外部环境绝对路径；
- 非公开样本的内容、指标、截图、调参结论或对比细节；
- 模型缓存、真实输出目录、大二进制文件或本地台账；
- 未经验证的“真实推理成功”“效果提升”“公平对比”等结论；
- 完整异常堆栈、命令历史、内部 URL 或可还原敏感上下文的日志。

可公开写入：

- repo-relative 文件名；
- commit SHA、PR 号、分支名；
- 测试命令和通过数量；
- 安全错误类别；
- 公开 fixture 或 synthetic 输入说明；
- 截图用途说明；
- 可回退提交。

任何不确定是否可公开的信息，默认不公开。

## 11. 每个任务的完成检查

在接受 AI 结果前逐项回答：

- [ ] 它只改了授权文件吗？
- [ ] 它是否确认了当前实现，而不是凭记忆？
- [ ] 它真实运行了什么命令？
- [ ] 结果中有测试、样例或截图证据吗？
- [ ] 有没有吞异常、写死路径或覆盖输出？
- [ ] 有没有改变公共契约却未通知？
- [ ] 有没有引入不必要依赖或外部访问？
- [ ] 对用户体验或效果的结论是否仍需人工验证？
- [ ] 失败时能否回滚？
- [ ] 交接是否只包含公开安全内容？

任何一项答不出来，就不能把该任务标为完成。

## 12. GitHub Issue 总线协议

当 A/B/C 各自使用独立 AI 客户端时，统一用一个 GitHub Issue 做消息总线。总线只负责派单、领取、活性检查、阶段检查和交接；不要把它变成聊天记录、密钥仓库或素材索引。

### 12.1 消息类型

| 标签 | 发送者 | 用途 | 行动规则 |
|---|---|---|---|
| `[ROUTER-HOLD]` | 人或 C | 冻结当前阶段，防止 AI 自行开工 | 只能 ACK 或报告状态；不改代码、不推分支 |
| `[AGENT-ACK]` | A/B/C | 客户端接入确认 | 写清角色、Issue 可读/可写、当前分支和监听能力 |
| `[DISPATCH]` | 人或被授权的 C | 唯一有效派单 | 必须包含 `dispatch_id`、目标角色、授权文件、禁止事项和验收命令 |
| `[CLAIM]` | 目标角色 | 领取派单 | 每个角色对每个 `dispatch_id` 只回复一次，先 CLAIM 再执行 |
| `[PING]` | 人或 C | 监听活性检查 | 必须带 `sequence`，目标角色只回对应 `[PONG]` |
| `[PONG]` | 目标角色 | PING 回执 | 同一 `sequence` 只回一次，不触发代码动作 |
| `[CHECKPOINT]` | 执行角色 | 阶段进展 | 有新增事实时发送，列真实测试、阻塞或风险变化 |
| `[HANDOFF]` | 执行角色 | 派单完成交接 | 列提交、PR、测试、证据边界、已知风险和回滚方式 |
| `[BLOCKED]` | 执行角色 | 无法继续 | 说明阻塞条件、已尝试验证和需要的新授权 |
| `[ROUTER-SUMMARY]` | C | 总线阶段总结 | 汇总 CLAIM/PONG/HANDOFF 状态，不替代各角色测试证据 |

没有明确 `[DISPATCH]` 且目标角色不匹配时，AI 只读 Issue 并安静报告“无本角色行动”。产品代码任务在 `[ROUTER-HOLD]` 下保持 HOLD，除非后续派单明确解除对应范围。

### 12.2 `dispatch_id`、`sequence` 与幂等

- `dispatch_id` 是派单唯一键，格式建议为 `AR-R<round>-<role>-<number>`。
- `[PING]` 必须带 `sequence`，格式建议为 `<dispatch_id>-<role>-PING-<number>`。
- AI 看到已 CLAIM 的同一 `dispatch_id` 时，不重复 CLAIM。
- AI 看到已 PONG 的同一 `sequence` 时，不重复 PONG。
- 重复轮询同一 Issue 不能制造重复评论。
- `[CHECKPOINT]` 可重复，但每次必须有新增事实。
- `[HANDOFF]` 每个 `dispatch_id` 只发一次；后续修复必须由新的派单触发。

### 12.3 监听规则

- 监听只读目标 Issue，不扫描私信、通知中心、其他仓库或本机私人目录。
- 默认轮询间隔和有效期必须在 ACK/CLAIM 中写清。
- 到期后自动静默，除非收到新的明确授权。
- 轮询期间若没有目标角色的 `[PING]` 或 `[DISPATCH]`，不要评论刷屏。
- 监听到新派单后，先校验目标角色、授权人、文件范围和禁止事项，再 `[CLAIM]`。
- 自动化过期、被手动停止或客户端能力不足时，用 `[BLOCKED]` 或下一次人工状态说明，不伪装仍在监听。

### 12.4 精确授权与角色所有权

每个 `[DISPATCH]` 必须写明：

- 目标角色和 GitHub 用户；
- 基线分支和当前 SHA；
- 允许修改文件的精确列表；
- 只读参考文件；
- 禁止修改范围；
- 必跑验收命令；
- 是否允许访问外部环境、模型、网络和公开样例。

若问题落在别人文件里，本角色不越权修复；发 `[CHECKPOINT]` 或 `[BLOCKED]`，附最小复现和建议 owner。公共契约、依赖、启动入口、样例策略和合并策略默认由 C 或人统一派单。

### 12.5 PR、提交与合并边界

- A/B 在自己的功能分支提交；文档或协议类任务若要求独立 PR，必须从指定基线新建分支。
- 不重写历史、不强制推送、不自动合并、不关闭他人 PR。
- 一个派单内不得混入未授权文件。
- 跨 PR 任务要分别提交、分别说明测试。
- PR 目标分支按派单执行，通常为集成分支。
- HANDOFF 必须列出分支、完整提交 SHA、PR 链接、修改文件、测试结果、证据边界、已知风险和回滚方式。
- C 负责最终整合和冲突语义判断；A/B 不把本地通过当作已集成。

### 12.11 脱敏示例

A 的脱敏示例：

```text
[HANDOFF]
role=A
dispatch_id=AR-R3-A-001
pr=#12
branch=feat/a-audio-core
head=<sha>
status=READY_FOR_REVIEW
changed_files=core/example_backend.py; tests/test_example_backend.py
implemented=added fail-closed backend state handling and safe error categories
```
